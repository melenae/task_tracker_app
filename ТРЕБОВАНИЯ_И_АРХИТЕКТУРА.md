# 1. СБОР ТРЕБОВАНИЙ КЛИЕНТА

## 1.1. Обзор требований клиента (Client Requirements Overview)

### 1.1.1. Бизнес-требования

**Основная цель проекта:**
Разработка веб-приложения для расширения функциональности десктопного приложения ERP-tools, обеспечивающего профессиональную командную работу по внедрению ERP-систем.

**Ключевые бизнес-потребности:**
1. Централизованное управление задачами проекта в веб-интерфейсе
2. Интеграция с внешними системами (1С, другие ERP-системы) для синхронизации данных
3. Управление проектами с разделением по командам и ролям
4. Контроль доступа и прав пользователей
5. Отслеживание прогресса выполнения задач

**Целевая аудитория:**
- Проектные менеджеры
- Разработчики ERP-систем
- Аналитики
- Тестировщики
- Клиенты (заказчики)

### 1.1.2. Функциональные требования клиента

**Управление задачами:**
- Создание, редактирование и удаление задач
- Назначение ответственных исполнителей
- Установка приоритетов и дедлайнов
- Отслеживание статусов выполнения
- Добавление комментариев к задачам
- Фильтрация и поиск задач

**Управление проектами:**
- Создание и управление проектами
- Формирование команд проекта с назначением ролей
- Привязка задач к проектам
- Управление спринтами

**Управление компаниями и клиентами:**
- Ведение базы компаний-клиентов
- Управление рабочими группами клиентов
- Привязка задач к компаниям и услугам

**Интеграция:**
- Двунаправленная синхронизация данных с внешними системами через Apache Kafka
- Автоматическое создание задач из внешних систем
- Отправка событий о изменениях задач во внешние системы

## 1.2. Сводка системных требований (System Requirements Summary)

### 1.2.1. Технические требования

**Backend:**
- Python 3.12+
- Django 5.2.8
- PostgreSQL (любая актуальная версия)
- Apache Kafka 7.5.0
- Zookeeper 7.5.0
- Redis (для кэширования)

**Infrastructure:**
- Docker и Docker Compose для оркестрации сервисов
- Поддержка контейнеризации всех компонентов

**Интеграция:**
- Apache Kafka для асинхронной обработки сообщений

- Обработка событий в реальном времени

### 1.2.2. Требования к производительности

- Асинхронная обработка сообщений Kafka в отдельном потоке
- Оптимизация запросов к базе данных (select_related, prefetch_related)

### 1.2.3. Требования к безопасности

- Аутентификация через Django Auth
- Система ролей и прав доступа
- Контроль доступа через permitted_accounts

## 1.4. Операционный рабочий процесс (Operational Workflow)

### 1.4.1. Рабочий процесс создания задачи

```
1. Пользователь создает задачу через веб-интерфейс
   ↓
2. Заполнение полей задачи (название, описание, приоритет, дедлайн)
   ↓
3. Выбор проекта, компании, ответственного
   ↓
4. Сохранение задачи в базу данных
   ↓
5. Автоматическая генерация external_id
   ↓
6. Django Signal (post_save) перехватывает событие
   ↓
7. KafkaService отправляет событие 'created' в топик 'issues-events'
   ↓
8. Внешняя система (1C) получает событие через Kafka Consumer
```

### 1.4.2. Рабочий процесс получения задачи от 1C

```
1. Внешняя система (1C) создает задачу
   ↓
2. 1C отправляет сообщение в топик 'issues-events-1c'
   ↓
3. Django Kafka Consumer получает сообщение (фоновый поток)
   ↓
4. Парсинг headers сообщения в словарь
   ↓
5. IssuesService.create_issue_from_1c() обрабатывает данные
   ↓
6. Маппинг полей от 1C к Django (Content → content, статусы, приоритеты)
   ↓
7. Поиск пользователей по external_id
   ↓
8. Создание задачи в базе данных
   ↓
9. Задача отображается в веб-интерфейсе
```

### 1.4.3. Рабочий процесс управления проектом

```
1. Администратор создает проект
   ↓
2. Назначение менеджера проекта
   ↓
3. Добавление участников в команду проекта
   ↓
4. Назначение ролей участникам
   ↓
5. Привязка компаний к проекту
   ↓
6. Привязка баз данных к проекту
   ↓
7. Создание спринтов для проекта
   ↓
8. Создание задач в рамках проекта
```

### 1.4.4. Рабочий процесс аутентификации

```
1. Пользователь вводит email и пароль
   ↓
2. Django Auth проверяет учетные данные
   ↓
3. При успешной аутентификации создается сессия
   ↓
4. Автоматическое создание профиля Users (если не существует)
   ↓
5. Определение роли пользователя (admin/user)
   ↓
6. Загрузка разрешенных аккаунтов (permitted_accounts)
   ↓
7. Перенаправление на главную страницу с соответствующими правами
```

# 3. АНАЛИЗ ТРЕБОВАНИЙ (REQUIREMENT ANALYSIS)

## 3.1. Спецификации уровня L1 (L1 Specifications)

### 3.1.1. Функциональные требования высокого уровня

**FR-1: Управление задачами**
- Система должна позволять создавать, редактировать и удалять задачи
- Система должна поддерживать отслеживание статусов задач
- Система должна поддерживать установку приоритетов и дедлайнов

**FR-2: Управление проектами**
- Система должна позволять создавать и управлять проектами
- Система должна поддерживать формирование команд проекта
- Система должна поддерживать назначение ролей участникам

**FR-3: Интеграция с внешними системами**
- Система должна отправлять события о изменениях задач во внешние системы
- Система должна получать события от внешних систем и создавать задачи
- Система должна поддерживать двунаправленную синхронизацию данных

**FR-4: Аутентификация и авторизация**
- Система должна обеспечивать аутентификацию пользователей
- Система должна поддерживать систему ролей и прав доступа
- Система должна контролировать доступ к ресурсам

### 3.1.2. Нефункциональные требования высокого уровня

**NFR-1: Производительность**
- Система должна обрабатывать запросы в течение 2 секунд
- Система должна поддерживать асинхронную обработку сообщений
- Система должна оптимизировать запросы к базе данных

**NFR-2: Надежность**
- Система должна иметь uptime не менее 99%
- Система должна обрабатывать ошибки gracefully
- Система должна поддерживать retry механизм для Kafka

**NFR-3: Безопасность**
- Система должна обеспечивать защиту от SQL injection
- Система должна обеспечивать CSRF защиту
- Система должна шифровать пароли пользователей

## 3.2. Спецификации уровня L2 (L2 Specification)

### 3.2.1. Детальные функциональные требования

**FR-1.1: Создание задачи**
- Пользователь должен иметь возможность создать задачу через веб-интерфейс
- Задача должна содержать: название, описание, статус, приоритет, дедлайн
- Система должна автоматически генерировать external_id для задачи
- Система должна отправлять событие 'created' в Kafka после создания задачи

**FR-1.2: Редактирование задачи**
- Пользователь должен иметь возможность редактировать все поля задачи
- Система должна отправлять событие 'updated' в Kafka после обновления задачи
- Система должна проверять права доступа перед редактированием

**FR-1.3: Изменение статуса задачи**
- Пользователь должен иметь возможность изменить статус задачи
- Доступные статусы: new, in_progress, waiting, testing, done, closed
- Система должна отправлять событие 'status_changed' в Kafka

**FR-2.1: Создание проекта**
- Администратор должен иметь возможность создать проект
- Проект должен быть привязан к аккаунту
- Проекту должен быть назначен менеджер

**FR-3.1: Отправка событий в Kafka**
- Система должна отправлять события в топик 'issues-events'
- Формат события: JSON с полями event_type, issue_id, timestamp, data, source
- Система должна обрабатывать ошибки отправки

**FR-3.2: Получение событий от 1C**
- Система должна получать события из топика 'issues-events-1c'
- Система должна парсить headers сообщения
- Система должна маппить поля от 1C к Django моделям

### 3.2.2. Детальные нефункциональные требования

**NFR-1.1: Время отклика**
- Время отклика веб-интерфейса: не более 2 секунд
- Время обработки Kafka сообщений: не более 5 секунд
- Время выполнения запросов к БД: не более 1 секунды

**NFR-2.1: Обработка ошибок**
- Система должна логировать все ошибки
- Система должна обрабатывать недоступность Kafka gracefully
- Система должна поддерживать retry для Kafka операций

## 5.2. Архитектурные паттерны

### 5.2.1. Используемые паттерны

| Паттерн | Описание | Применение |
|---------|----------|------------|
| **MVC (Model-View-Controller)** | Разделение на модели, представления и контроллеры | Django архитектура |
| **Service Layer** | Вынесение бизнес-логики в сервисы | KafkaService, IssuesService |
| **Repository Pattern** | Абстракция доступа к данным | Django ORM |
| **Observer Pattern** | Уведомление об изменениях | Django Signals |
| **Singleton Pattern** | Единственный экземпляр сервиса | KafkaService (class methods) |
| **Factory Pattern** | Создание объектов через фабрики | Django Model factories |
| **Event-Driven Architecture** | Обработка событий асинхронно | Kafka интеграция |

### 5.2.2. Принципы проектирования

- **Separation of Concerns** - разделение ответственности между слоями
- **DRY (Don't Repeat Yourself)** - переиспользование кода
- **SOLID принципы** - следование принципам объектно-ориентированного проектирования
- **Dependency Injection** - внедрение зависимостей через Django settings
- **Single Responsibility** - каждый класс имеет одну ответственность
